# IS115 — Last-Mile Delivery Planning

Dispatch policies for a single-hub, ten-vehicle parcel delivery problem.
Compares a supplied FIFO baseline against five proposed policies across
20 historical days, using on-time delivery rate as the primary metric.

## 3. Running the Baseline (Day 1)

From the project root:

```
python -m simulator --policy solution.policies.baseline --data data --day day_001 --output results/baseline/day_001
```

This writes `results/baseline/day_001/log.txt` — the JSON Lines event log.

Then compute metrics for that log:

```
python -m solution.performance_monitor --data data --day day_001 --log results/baseline/day_001/log.txt
```

This writes `results/baseline/day_001/metrics.json` beside the log.

## 5. Running All Policies on All 20 Days

PowerShell (recommended in VS Code terminal):

```powershell
$policies = @(
    "baseline",
    "nearest_neighbour",
    "earliest_deadline",
    "knapsack_dispatch",
    "heuristic_best",
    "window_aware_dispatch"
)

foreach ($pol in $policies) {
    foreach ($d in 1..20) {
        $day = "day_{0:D3}" -f $d
        $out = "results/$pol/$day"
        Write-Host "=== $pol / $day ==="
        python -m simulator --policy "solution.policies.$pol" --data data --day $day --output $out
        if ($LASTEXITCODE -ne 0) { Write-Host "SIMULATOR FAILED: $pol $day" -ForegroundColor Red; continue }
        python -m solution.performance_monitor --data data --day $day --log "$out/log.txt"
        if ($LASTEXITCODE -ne 0) { Write-Host "MONITOR FAILED: $pol $day" -ForegroundColor Red }
    }
}
```

Runtime: roughly 10 minutes on a typical laptop (120 simulator runs
plus 120 monitor runs).

cmd equivalent (fragile, prefer PowerShell):

```
for %P in (baseline nearest_neighbour earliest_deadline knapsack_dispatch heuristic_best window_aware_dispatch) do (
  for /L %d in (1,1,20) do (
    setlocal enabledelayedexpansion
    set "D=00%d"
    set "DAY=day_!D:~-3!"
    python -m simulator --policy solution.policies.%P --data data --day !DAY! --output results/%P/!DAY!
    python -m solution.performance_monitor --data data --day !DAY! --log results/%P/!DAY!/log.txt
    endlocal
  )
)
```

## 6. Generating the Summary Table

After the batch run, aggregate per-day metrics into a single summary:

```
python summarise_metrics.py
```

This reads every `results/<policy>/day_*/metrics.json` and writes:

- `results/algorithms_summarised_metrics.json` — structured summary
- `results/algorithms_summarised_metrics.txt` — human-readable table

Console output columns: Total, On-Time%, Early%, Late%, Complete%,
Late/Deliv, Trips.

Aggregation uses summed raw counts across all 20 days before dividing
(not averaged daily rates), which is the correct weighted figure when
daily volume varies.

## 7. Metric Definitions

Primary metric — On-Time Delivery Rate (OTR):

Deliveries whose actual time falls inside the parcel's preferred window,
divided by all parcels that arrived during the day (including
undelivered ones). The denominator choice makes the metric
non-trivial: it penalises both late deliveries and abandoned parcels.

Supporting metrics:

| Metric                        | Definition                                              |
|-------------------------------|---------------------------------------------------------|
| Completion rate               | Delivered ÷ all arrived                                 |
| Early rate                    | Delivered before `window_start` ÷ all arrived           |
| Late rate                     | Delivered after `window_end` ÷ all arrived              |
| Late minutes per delivered    | Total lateness minutes ÷ total delivered parcels        |
| Total distance (km)           | Sum of route length across all trips in the day         |
| Number of trips               | Count of `hub_departure` events in the log              |

All rates sum to 1.0 (on-time + early + late + undelivered), which
serves as a consistency check.

## 8. Results Summary

The complete per-policy results table is in
`results/algorithms_summarised_metrics.txt`. The main findings:

- `knapsack_dispatch` achieves the highest on-time delivery rate with
  competitive distance and is the recommended policy.
- `nearest_neighbour` achieves the highest completion rate and lowest
  total distance, but delivers a substantial fraction of parcels
  before their window opens — not a service win.
- `earliest_deadline` nearly doubles baseline OTR but has a high late
  rate among improved policies due to urgency-scatter on the route.
- `heuristic_best` underperforms its constituents, illustrating that
  combining heuristics does not guarantee dominance.
- `baseline` (FIFO) delivers only a small fraction on time, motivating
  the project.

See the full report for detailed analysis.

## 9. Reproducibility Notes

- The `simulator/` and `data/` directories are provided and unmodified.
- `solution/policies/baseline.py` is the original supplied file,
  unchanged.
- Dispatch policies access only the `parcel` and `context` dictionaries
  passed by the simulator; they do not read any files during simulation.
- Hard constraints (capacity 30, range 320 km, 18:00 return cutoff) are
  enforced at three layers: inside each policy's selection logic,
  inside `helpers.route_feasible`, and finally by the simulator's own
  `_validate_route`. A policy that ever attempted to return an
  infeasible route would be rejected by the simulator with an error;
  no policy in this repository does so.
- Results in `results/` were generated on the standard `data/` inputs
  with a fixed configuration; re-running the commands above reproduces
  the same logs and metrics.
